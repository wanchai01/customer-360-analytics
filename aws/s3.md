# S3 Data Lake — Design & Rationale

## Bucket Layout

```
s3://customer-360-data/
├── raw/                      # CSV / JSON, exactly as produced by source systems
│   ├── customers/batch_date=YYYY-MM-DD/customers.csv
│   ├── products/batch_date=YYYY-MM-DD/products.csv
│   ├── orders/batch_date=YYYY-MM-DD/orders.csv
│   ├── order_items/batch_date=YYYY-MM-DD/order_items.csv
│   ├── payments/batch_date=YYYY-MM-DD/payments.csv
│   ├── website_events/batch_date=YYYY-MM-DD/website_events.json
│   ├── customer_support/batch_date=YYYY-MM-DD/customer_support.csv
│   ├── marketing_campaigns/batch_date=YYYY-MM-DD/marketing_campaigns.csv
│   └── campaign_interactions/batch_date=YYYY-MM-DD/campaign_interactions.csv
├── processed/                # Parquet, cleaned + type-cast (Phase 5 PySpark output)
│   ├── customers/batch_date=YYYY-MM-DD/
│   ├── orders/batch_date=YYYY-MM-DD/
│   └── events/batch_date=YYYY-MM-DD/
└── curated/                  # Parquet, business-ready Gold tables (Phase 8-9 output)
    ├── customer_360/
    ├── customer_rfm/
    ├── customer_segments/
    └── customer_metrics/
```

`batch_date=YYYY-MM-DD` (Hive-style partitioning) is used consistently
across raw and processed so Spark/Athena/Glue can partition-prune on
date without a separate partitioning scheme per layer. `curated/` is
not batch-partitioned — Gold tables are full-refresh snapshots of
"the current truth" (e.g. `customer_360` has exactly one row per
customer, not one per day), so partitioning by date would only add
storage cost with no query benefit.

## Why Parquet for processed/curated (and not raw)

- **Columnar storage**: analytical queries (`SUM(total_amount)`,
  `AVG(resolution_time)`) read only the columns they need instead of
  full rows — a 10-column table where a query touches 2 columns reads
  roughly 1/5th the bytes CSV would require.
- **Predicate pushdown**: Parquet stores per-column statistics
  (min/max) in its footer, so engines like Spark/Athena can skip
  entire row groups that can't match a filter (e.g. `order_date >=
  '2026-01-01'`) without decompressing them.
- **Compression**: columnar data compresses far better than row-based
  CSV (similar values sit next to each other) — typically 3-10x
  smaller on disk, which is both a storage-cost and an I/O-time win.
- **Schema + type safety**: Parquet embeds its schema (column names,
  types) in the file; CSV does not, which is why every "invalid date /
  negative amount" data-quality problem in this project originates in
  the CSV/JSON raw layer, never in Parquet.

Raw stays CSV/JSON deliberately: it should be a byte-for-byte record
of what the source system actually sent, before any interpretation —
useful for replaying the pipeline from scratch or auditing what was
originally received if a downstream bug is ever suspected.

## Local Development: MinIO

Real AWS S3 costs money and requires an AWS account; this project
runs an S3-*compatible* server (MinIO) in Docker Compose instead, so
the whole pipeline works locally with zero AWS spend.

The `data_lake/` Python package (`s3_client.py`, `lake_paths.py`,
`sync_to_lake.py`) is written entirely against the boto3 S3 API — it
has no MinIO-specific code path. The only difference between "local"
and "AWS" is one environment variable:

| Environment | `AWS_S3_ENDPOINT_URL`         | Credentials                     |
|-------------|-------------------------------|----------------------------------|
| Local (MinIO)| `http://minio:9000`          | `MINIO_ROOT_USER` / `_PASSWORD` |
| AWS          | *(unset)*                     | Real IAM access key / secret    |

Moving to AWS later means: create the real bucket, set real IAM
credentials in `.env`, delete/unset `AWS_S3_ENDPOINT_URL` — no
application code changes.

## Security (AWS, when deployed)

- **Block Public Access** enabled at the bucket level — this bucket
  is never meant to serve content directly to the internet.
- **Server-side encryption** (SSE-S3 or SSE-KMS) enabled by default
  on the bucket, so every object is encrypted at rest automatically.
- **IAM least privilege**: the pipeline's IAM role gets
  `s3:GetObject`/`s3:PutObject`/`s3:ListBucket` scoped to
  `arn:aws:s3:::customer-360-data/*` only — not account-wide S3
  access, and no `s3:DeleteBucket` or bucket-policy permissions
  (see `aws/iam.md`).
- **Bucket policy** denies any request that isn't using TLS
  (`aws:SecureTransport = false` → Deny).

## Cost & Lifecycle (AWS, when deployed)

| Layer      | Storage class strategy                                              |
|------------|------------------------------------------------------------------------|
| `raw/`     | S3 Standard for 30 days (still might be re-processed), then transition to S3 Glacier Instant Retrieval — raw batches are rarely re-read after the processed layer has consumed them, but are kept for audit/replay. |
| `processed/`| S3 Standard for 90 days, then S3 Standard-IA — occasionally re-read for backfills, but not part of daily query paths. |
| `curated/` | S3 Standard indefinitely — this is what Power BI and analysts query directly; it must stay in the fastest tier. |

A lifecycle rule transitioning `raw/*` to Glacier Instant Retrieval
after 30 days is the single highest-leverage cost control here,
since raw is CSV/JSON (uncompressed, larger) and is the layer with
the least ongoing read traffic once a batch has been processed.

## Availability & Scalability

S3 provides 99.99% availability and 11 nines of durability by design
(data replicated across ≥3 Availability Zones) — this is inherited
for free, not something this project needs to engineer. Scalability
is likewise not a concern the application layer needs to handle: S3
has no meaningful limit on object count or total bucket size, and
request-rate scaling is automatic (S3 auto-partitions high-throughput
prefixes internally). The practical scaling considerations for this
project are all downstream of S3 — how fast Spark can read/write
Parquet at 50M+ row scale (Phase 5) and how large a warehouse
PostgreSQL/RDS instance needs to be (Phase 3, `aws/rds.md`).
